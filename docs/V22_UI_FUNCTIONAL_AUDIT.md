# NemoGuard V22: UI and functional review

## Scope and evidence

Reviewed the restored V22 tree at commit `d85e959` and the subsequent local UI changes. This is a source-level review of the principal product surfaces and a targeted desktop preview using synthetic data. It is not a production data validation, penetration test, exhaustive end-to-end audit, or measurement of RCA accuracy. Findings below are observations of code behavior unless marked as a recommendation or a documented limitation. Do not treat illustrative preview data as production evidence.

## P0: operational trust and safety

1. **A failed snapshot query can look like a valid zero.** `backend/app/domain/operations_intelligence.py` catches every exception in `_rows` and returns `[]`. This affects essential as well as optional tables. A query or schema failure can therefore produce zero incidents, missing evidence, or a reassuring empty state instead of a visibly degraded projection. Distinguish mandatory-query failure from optional data unavailability; return per-source completeness and failure metadata, log failures without leaking sensitive data, and test database failures on both supported backends.
2. **Recovery formulation indicators overstate evidence.** `renderer/src/components/dashboard/RecoveryRail.tsx` marks “Blast radius calculated” complete when any evidence exists, rather than when impact data exists. It also treats `APPROVED` as executed for the formulation checklist. `IncidentWorkspace.tsx` similarly includes `APPROVED` in `isPlanExecuted` when computing `canApprove`. Define separate plan approval, execution and verification states from authoritative API fields, and test every transition, retries and failure states. This is a UI-state finding, not proof of an unauthorized backend action.
3. **Intelligence mislabels a metric.** `renderer/src/pages/IntelligencePage/IntelligencePage.tsx` counts incidents whose status is `RESOLVED` today but labels the result “verified recoveries”; the calculation does not inspect independent verification. Rename the metric to resolved incidents or source a verified count from authoritative verification results. Its first-load error path can also display zero-valued cards and a clear-queue empty state alongside an error banner; show unavailable values when no successful response has been received.
4. **Preserve authority boundaries.** `V22_KNOWN_LIMITATIONS.md` states forwarded email is unverified external evidence, coverage is data presence rather than calibrated correctness, and live remediation is limited. Maintain those distinctions across Commander, recovery and overview; test that missing evidence or low authority cannot be presented as independent verification.

## P1: correctness and operator workflows

5. **Overview drill-downs are misleading.** `ProductionOverviewPage.tsx` links open incidents to `/app/incidents?state=open`, but `IncidentsPage.tsx` always requests `state=all` and does not read the filter. Agent cards link using `?agent=...`, but `AgentOperationsPage.tsx` does not read that parameter. Implement and test URL-driven filters or remove unsupported parameters and adjust labels.
6. **Incident discovery and keyboard access.** `IncidentsPage.tsx` makes table rows clickable without a native link/button, so keyboard users cannot activate them in the same way. Severity sort uses alphabetical string order rather than an explicit severity ranking. The selected incident is local component state, not a shareable URL. Add semantic actions, normalized severity ranking, filters, pagination and deep links.
7. **Freshness and polling.** Overview polls the full snapshot every 15 seconds; `useNotifications.ts` independently polls it every 10 seconds and suppresses errors, keeping the last notification state without its own freshness indicator. `Dashboard.tsx` polls two incident lists every two seconds; other pages poll every five seconds. Share and deduplicate queries, prevent overlapping/out-of-order responses, pause or back off when hidden/offline, expose last-success and failure states, and assess an event-driven transport. Measure load before choosing an interval.
8. **Snapshot scalability and metric completeness.** `operations_intelligence.py` reads incident, alert, plan, evidence and hypothesis histories into memory; impacts and verifications are loaded across incidents and filtered afterward. Audit events are limited to 500, so agent event counts and median triage can be incomplete on busy tenants. Move scoping, time windows and aggregations into indexed queries; make truncation and metric definitions visible and test with larger datasets.
9. **Alert Inbox workflow.** `AlertInboxPage.tsx` shows at most 200 recent accepted messages and has no pagination, search or queue filters. Add server-side pagination/filtering, selection persistence, visible freshness and processing outcome details. Preserve its existing warnings about untrusted email, promotion semantics and uncertain retry outcomes.
10. **Agent Operations semantics.** `AgentOperationsPage.tsx` fetches events when an incident is selected, but does not refresh that event history periodically; `LiveOperationsConsole` is passed `status="connected"` after a one-time successful fetch. Label it as a historical snapshot or implement a real live stream with disconnected/reconnect and last-updated states. Honor or remove overview agent links.
11. **Time and counts.** Overview chart dates originate in UTC but are formatted from UTC midnight with the browser’s local timezone, which can display the prior date in western timezones. Define and display timezone and window semantics. Review the hard-coded “Last 30 days” shell badge: it is not connected to a global date filter and overview sections use multiple windows.
12. **Action clarity.** In `RecoveryRail.tsx`, every `FAILED` incident is labeled “VERIFICATION FAILED” regardless of the cause. Present the actual failure phase and evidence; distinguish approved, executing, verification passed/failed and manual action required. Confirm all action labels and disabled reasons with backend state-machine tests.
13. **Search and error feedback.** `CommandPalette.tsx` converts incident-fetch failures to an empty list, making a failed search look like no matches; it also limits fetched incidents to 50. Surface unavailable versus empty results, pagination and scope. `SettingsPage.tsx` has a switch with `role="switch"` and `aria-checked` but no programmatic accessible name; label it explicitly.

## P1: production readiness and evaluation

14. **Persistence and deployment.** `V22_KNOWN_LIMITATIONS.md` says the recommended aXet MySQL-compatible backend is not implemented and warns against SQLite on shared internal storage. Confirm the deployment contract, implement and test a durable backend, migrations, backup/restore, concurrency and failover before production reliance. The documented Python Gateway cold-start issue is a platform dependency; validate current platform behavior rather than assuming it is still present.
15. **Integration and provenance.** The documented live intake path is Outlook forwarding, not comprehensive telemetry. Prioritize independently observed logs, job/run status, monitoring, CMDB/ownership and runbooks, retaining timestamps, source authority and tenant/workspace provenance. Unknown is safer than inferred healthy.
16. **Accuracy evaluation.** Build a reviewed, versioned dataset of representative incidents with evidence available at decision time and confirmed outcomes. Measure classification/correlation precision and recall, RCA ranking, unsupported claims, evidence sufficiency, recovery recommendations, false resolutions and calibration by severity and source. Include missing, stale, conflicting, adversarial and cross-tenant cases; track model/prompt/version drift and human correction outcomes.
17. **Security and resilience verification.** Add negative tests for roles and tenant/workspace isolation across all reads, events and mutations; test idempotency, concurrent retries, approval changes, stale plans, cancellation races and failed verification. Review token storage and session-expiry behavior against deployment policy. These are recommended tests, not claims of a confirmed exploit.

## P2: visual system and accessibility

18. **Consistency across pages.** The V22 overview and admin use a light-first card language, while incident, agent, intelligence, settings and inbox pages use older glass-panel/token treatments. Establish shared page headers, card hierarchy, spacing, tables, forms, empty/error/loading states and semantic status colors; audit both theme modes rather than assuming all hard-coded colors adapt.
19. **Icon family.** The navigation now uses custom sonar-family SVGs with visible labels. Extend a consistent stroke, optical sizing and distinct silhouette system to status, evidence, recovery and empty-state illustrations. Validate recognition at actual sizes; never use color or an icon alone to communicate critical status.
20. **Motion and loading.** Define motion tokens for navigation, page transitions, skeletons, asynchronous updates, success and errors. Keep motion short and purposeful; avoid synthetic percentage progress and continuous motion for static states. Verify both CSS and Framer Motion under `prefers-reduced-motion`. Use labeled status regions, reserve space to reduce layout shifts, and provide retry paths for initial load failures.
21. **Information density and contrast.** Several surfaces use 9–11px secondary text and truncated details. Raise minimum readable text sizes, test contrast in both themes, expose full details on demand, and review layout at 200% zoom and tablet/mobile widths. `HealthRow` uses a colored dot/title for state; provide a visible textual status as well.
22. **Accessible interactions.** Audit keyboard navigation and visible focus across tables, menus, drawers, tabs and dialogs, including focus return, escape, tab trapping, screen-reader names and error announcements. Add automated accessibility checks plus manual screen-reader testing. Verify the new mobile drawer at narrow widths and when the viewport changes while open.
23. **Charts and empty states.** Provide chart legends, text/table alternatives, timezone labels and clear no-data versus unavailable states. Avoid green “all clear” messages when inputs are missing or stale. Make empty states informative and task-oriented without implying operational health.
24. **Performance and deployment bundle.** `renderer/vite.config.ts` uses a single-file plugin with `inlineDynamicImports`; despite lazy route imports, deployment produces one large HTML bundle. Measure cold start, caching and aXet requirements; only switch to split assets if the platform supports them. The current build emits CSS gradient syntax warnings and lint reports existing warnings.

## Suggested sequencing

1. Correct false/unknown operational states, recovery status wording and the verified-recovery metric; add failure and state-transition tests.
2. Repair drill-downs, semantic keyboard controls, freshness and polling behavior.
3. Establish durable persistence and approved independent integrations, with provenance and tenant isolation.
4. Build an evaluation set and measure classification, correlation, RCA and recovery accuracy before expanding automation.
5. Roll out the shared visual system, custom icons, accessible motion/loading states and responsive regression coverage across each active page.

## Validation performed during this review

- Frontend production build and lint passed after the icon and mobile-focus changes; lint reported 21 warnings and zero errors. The build also reported existing single-file and CSS gradient warnings.
- A 900×600 synthetic-data preview confirmed readable Commander Brief contrast, custom navigation icons, and that the Incidents sidebar link navigates. This was not a test of production APIs or all viewport sizes.
- Mobile drawer keyboard focus behavior, reduced motion, other viewport sizes, and production data require further manual or automated validation.
