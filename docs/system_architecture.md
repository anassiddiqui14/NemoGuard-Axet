# System Architecture Overview

This document outlines the architecture, components, and integration of the `NemoGuard Pipeline Copilot` project. It serves as a technical overview for developers and engineers aiming to understand or extend the platform.

---

## 1. Core Architecture & Design Philosophy
The system is built as an **Agentic Autonomous Operations Platform** for data engineering pipelines. 
Instead of a monolithic script, it uses an orchestrator pattern where a central React UI acts as the command center, utilizing discrete tools (via MCP patterns) to gather context, and a powerful LLM (NVIDIA Nemotron via NemoClaw Agents) to perform reasoning and remediation.

### The Presentation Layer (React + Vite)
To achieve an enterprise-grade experience, the presentation layer is built as a single-page application (SPA):
- **Incident Commander Dashboard (`frontend/src/components/Dashboard.tsx`):** The primary operator dashboard. It uses React, Vite, and TailwindCSS to deliver a clean, light-mode SaaS aesthetic featuring custom metric cards, dynamic causal chain visualizers, and a live SSE (Server-Sent Events) terminal for Agent Activity and Tool Traces.
- **Scenario Lab (`frontend/src/components/ScenarioLab.tsx`):** A simulator panel that allows operators to inject fully synthetic, highly realistic pipeline incidents (e.g., Schema Regressions, Compute Crashes) into the environment.

---

## 2. Data Layer & Tooling

### Synthetic Pipeline Database (`data/generated/pipeline.db`)
The backbone is an SQLite database containing synthetic but highly realistic pipeline execution data modeling a complex data warehouse environment:
- **`job` & `dependency` tables:** Maps the topology of the pipeline (e.g., extracting from AWS, transforming in EDW, loading to BWS) and tracking upstream/downstream dependencies.
- **`execution` & `log_event` tables:** Stores historical runs and detailed execution logs.
- **`incident` & `alert` tables:** The queue of active incidents and grouped alerts.
- **`audit_event` & `action_plan` tables:** Stores the live thought process and final runbook formulations generated by the AI agents.

### Agentic Tools (`src/tools/read_tools.py`)
We built a suite of Python classes that act as the agent's "hands and eyes." These tools encapsulate complex SQL queries into simple functions exposed to the NemoClaw agents:
- `get_run_timeline(run_id)`: Extracts raw log traces for a specific failure.
- `get_job_graph(job_id)`: Traverses the dependency table to find all downstream jobs blocked by the current failure.
- `fetch_filtered_alerts()`: Retrieves the current active queue.

*Note on Architecture: These tools are designed with the **Model Context Protocol (MCP)** in mind, making them easily registrable in sandboxed environments like NemoClaw.*

---

## 3. The Generative AI Brain & Backend

The core intelligence happens when an incident is triaged by the **NemoClaw Agent Runtime**.

1. **REST API & SSE (FastAPI):** The backend (`src/api/main.py`) exposes standard REST endpoints for the React frontend, as well as an EventSource endpoint (`/api/v1/incidents/{incident_id}/events/stream`) that streams live `audit_event` rows back to the UI.
2. **Context Gathering:** The Python orchestrator (`src/domain/orchestrator.py`) triggers specialized agents (Commander, RCA, Impact, Runbook, Safety, Verifier) based on the incident state.
3. **Inference (NVIDIA NIM):** The agents make requests to the NVIDIA NIM API (powered by models like `nemotron-4-340b-instruct`) to synthesize the context and generate structured JSON recovery plans.
4. **Dynamic Output:** The backend updates the database with the generated data, which the UI parses into specific visual elements:
   - **Causal Chain:** The AI's root cause hypothesis mapped into a visual timeline.
   - **Business Impact:** Blocked Data Products and SLA Runways.
   - **Recovery Action:** The specific runbook steps (e.g., "Deploy Fallback Schema") locked behind a human-in-the-loop **Approval Gate**.

---

## 4. Known Constraints & Future Improvements
- **Synchronous LLM Calls:** Some orchestration processes currently block the API thread while waiting for the LLM to generate the final JSON payload. Future iterations should move these to background Celery/Redis workers.
- **Mocked Remediation:** While the AI generates a highly technical runbook, clicking "Approve & Execute" currently transitions the state to executed but relies on mocked integration rather than actually mutating external infrastructure.
